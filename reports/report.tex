\section{Introduction}
Weather patterns in India vary significantly across regions due to differences
in geography, proximity to the coast, and elevation. Understanding these
differences over a long time period can give useful insights into how local
climates behave and whether any trends are visible over recent decades.

This project analyses daily weather data for four Indian cities --- Mumbai,
Delhi, Dehradun, and Jodhpur --- over a 25-year period from 2000 to 2024.
The cities were chosen to cover a range of climate types: Mumbai is a coastal
city with high humidity, Delhi and Jodhpur are inland with more extreme
temperature swings, and Dehradun is a cooler hill station in the foothills
of the Himalayas. Data was sourced from the NOAA Global Summary of the Day
(GSOD) database, which provides freely available daily observations from
weather stations around the world.

The project covers the full pipeline from raw data collection to final
visualisation. This includes writing automated download scripts, building a
cleaning pipeline to handle missing values and unit conversions, running
seasonal and interannual trend analysis, detecting anomalies, and developing
an interactive dashboard to present the results. The goal was not just to
produce plots, but to make sure each step of the pipeline was reproducible,
well-documented, and easy to understand.

\section{Related Work}
The NOAA Global Summary of the Day (GSOD) database is one of the most
widely used sources for long-term daily weather analysis due to its
consistent format, global station coverage, and free availability.
It has been used in a number of regional climate studies focusing on
temperature trends and precipitation variability, particularly in
monsoon-influenced regions like South Asia.

For separating seasonal and trend components in meteorological time
series, Seasonal-Trend decomposition using LOESS (STL) is a well-established
method introduced by Cleveland et al.\ (1990) \cite{cleveland1990}.
It is preferred over simpler moving average approaches because it handles
irregular seasonal shapes and is robust to outliers in the seasonal
component. This made it a natural choice for our cities, which have
strongly asymmetric monsoon-driven seasonal cycles.

Harmonic (Fourier) analysis is another standard approach in climatology
for quantifying dominant periodic cycles in temperature records. By
fitting sinusoidal components at annual and sub-annual frequencies,
it allows the fraction of variance explained by each cycle to be
quantified directly. This is particularly useful for comparing how
strongly seasonal the climate is across cities with different geographic
settings.

For anomaly detection in weather data, using the standard z-score
(based on mean and standard deviation) is known to be problematic
because extreme events such as floods or heatwaves inflate the mean,
making genuine anomalies appear less unusual than they are.
Leys et al.\ (2013) \cite{leys2013} recommend using the Median
Absolute Deviation (MAD) in place of the standard deviation for
exactly this reason, as it is far less sensitive to the outliers
one is trying to detect. Our cleaning pipeline follows this approach,
computing a robust z-score per variable per month using the monthly
median and MAD.


\section{Methods}

\subsection{Data}
The dataset used in this project is the NOAA Global Summary of the Day (GSOD),
a publicly available database that records daily weather observations from stations
around the world. Data was collected for four Indian cities --- Mumbai, Delhi,
Dehradun, and Jodhpur --- covering 25 years from 2000 to 2024.
Each city has a unique NOAA station ID: Mumbai (43003099999), Delhi (42182099999),
Dehradun (42110099999), and Jodhpur (42339099999).
Variables available include mean temperature, maximum and minimum temperature,
dew point, precipitation, wind speed, visibility, and pressure.

\subsection{Data Collection}
Data was downloaded directly from NOAA's servers using Python with no manual
steps involved. For each city, yearly CSV files were fetched from the following URL:

\begin{center}
\texttt{https://www.ncei.noaa.gov/data/global-summary-of-the-day/access/\{year\}/\{station\_id\}.csv}
\end{center}

A plain \texttt{requests.get()} call kept returning HTTP 503 errors because NOAA's
CDN blocks automated requests. The fix was to use a \texttt{requests.Session} with
browser-like headers (Chrome User-Agent, Accept-Language, Referer), along with retry
logic that waits and tries again if the server returns a 503 or 429 response.
A small random delay between requests was also added to avoid triggering rate limits.
To speed up the download, \texttt{ThreadPoolExecutor} was used to fetch 3 years
simultaneously instead of one by one.

The download code is split into one file per city inside the \texttt{raw\_data/} folder
(\texttt{mumbai\_raw.py}, \texttt{delhi\_raw.py}, \texttt{dehradun\_raw.py},
\texttt{jodhpur\_raw.py}). Each file exposes a single \texttt{get\_raw\_data()} function
that returns a combined dataframe for that city covering all 25 years.
To avoid re-downloading every time the code is run, the downloaded data is saved
as a \texttt{.nc} (NetCDF) file in \texttt{raw\_data/nc\_raw/} and loaded from
there on subsequent runs.

\subsection{Data Cleaning}
Raw NOAA data has several issues that need to be fixed before any analysis.
The cleaning pipeline is in the \texttt{cleaned\_data/} folder, with one file
per city. Each file imports raw data from the corresponding raw file, runs
the cleaning steps below in order, and saves the result as a \texttt{.nc} file
in \texttt{cleaned\_data/nc\_cleaned/}.

\begin{enumerate}

    \item \textbf{Date parsing.}
    The \texttt{DATE} column was parsed to datetime format and rows with
    unreadable dates were dropped. \texttt{YEAR} and \texttt{MONTH} columns
    were extracted for use in grouping later.

    \item \textbf{Replace fill values with NaN.}
    NOAA does not use NaN for missing data. Instead it uses large placeholder
    numbers --- 9999.9 for temperature, 99.99 for precipitation, 999.9 for
    wind and visibility. These were identified and replaced with NaN before
    any other step, otherwise they appear as real observations and break
    all statistics.

    \item \textbf{Remove duplicate dates.}
    Some years had more than one row for the same date. Duplicates were
    removed by keeping the first occurrence.

    \item \textbf{Unit conversion.}
    NOAA stores data in imperial units. All variables were converted to
    metric --- Fahrenheit to Celsius, inches to mm, knots to m/s, and miles
    to km. Columns were renamed to reflect the new units
    (\texttt{TEMP\_C}, \texttt{PRCP\_MM}, \texttt{WDSP\_MS} etc.).

    \item \textbf{Remove physically impossible values.}
    After unit conversion, a physical plausibility check was applied.
    Temperature above 60\textdegree C or below -90\textdegree C goes beyond
    any recorded Earth extreme. Negative rainfall or wind speed cannot exist.
    Rainfall above 2000mm in a single day exceeds the world record.
    Days where MAX temperature is lower than MIN are recording errors.
    Dew point above air temperature is physically impossible.
    All such values were set to NaN rather than corrected, since there is
    no reliable way to know what the actual reading should have been.

    \item \textbf{Anomaly detection.}
    A robust z-score was computed per variable per month using the median
    and MAD (Median Absolute Deviation) rather than mean and standard
    deviation. This choice is important --- using mean and SD on weather
    data is problematic because a real extreme event like a flood inflates
    the mean, making the event look less unusual than it actually is.
    The formula used is:
    \begin{align}
        z = \frac{0.6745 \times (x - \tilde{x})}{\mathrm{MAD}}
        \label{eq:zscore}
    \end{align}
    where $\tilde{x}$ is the monthly median and MAD is the median absolute
    deviation for that month. Values with $|z| > 3.5$ were flagged as
    anomalies and set to NaN, \emph{except} for rows corresponding to known
    historical extreme events (such as the 2005 Mumbai floods and the 2013
    Uttarakhand cloudbursts) which were protected from removal.

    \item \textbf{Select output columns.}
    The final dataframe keeps only the columns needed for analysis:
    DATE, CITY, YEAR, MONTH, TEMP\_C, MAX\_C, MIN\_C, DEWP\_C, PRCP\_MM,
    WDSP\_MS, MXSPD\_MS, GUST\_MS, and FRSHTT. Everything else is dropped.

\end{enumerate}

\subsection{Trend and Smoothing Methods}

Three complementary smoothing methods were implemented to analyse temperature
trends across the four cities.

\textbf{Rolling Window Average.}
A moving average was computed over 7, 30, and 90-day windows.
The 30-day window provided optimal noise reduction, achieving a 28--35\% reduction
in standard deviation, with Jodhpur benefiting most due to its high day-to-day
variability.

\textbf{STL Decomposition.}
Seasonal-Trend decomposition using LOESS (STL) separates temperature into trend,
seasonal, and residual components.
Coastal cities (Mumbai, Dehradun) show dampened seasonal amplitudes compared to
inland cities (Delhi, Jodhpur).
The trend component revealed a slight warming of +0.3--0.5\textdegree C in Delhi
and Mumbai over the analysis period.

\textbf{Harmonic Analysis.}
A Fourier-based decomposition was used to identify dominant periodic cycles.
The annual cycle explains 65--80\% of temperature variance, strongest in Delhi
(70\%) and weakest in Mumbai (62\%).
Progressive harmonic removal isolates residual anomalies by subtracting the
1st, 2nd, and 5th harmonics sequentially.

\textbf{Method Comparison.}
Rolling averages are best suited for operational monitoring; STL is preferable
for process understanding; harmonic analysis uniquely quantifies cycle strength.
All three methods agree on broad patterns but differ in sensitivity to short-term
variability.

\subsection{Trend Analysis Results}

Rolling average results show Jodhpur benefits most from smoothing (35\% noise
reduction), while Mumbai shows the least (28\%) due to its stable coastal climate.
The 30-day window emerged as the best default choice across all cities.

STL decomposition revealed that seasonal components account for 60--75\% of
temperature variation, with Delhi showing the strongest seasonal signal and Mumbai
the weakest. Dehradun showed the highest residual standard deviation, indicating
greater irregular variability linked to its topography.

Harmonic analysis shows that after removing the first three harmonics, the remaining
signal consists almost entirely of weather-scale noise and extreme events, providing
a clean anomaly signal. The cross-method comparison confirms agreement on broad
patterns but highlights method-specific sensitivities to short-term variability.

Trend analysis confirmed that method choice affects interpretation: 30-day rolling
averages optimise noise reduction, STL reveals coastal vs.\ inland seasonal
differences, and harmonic analysis quantifies the 65--80\% variance explained
by annual cycles.

The refinement results show that the chosen anomaly-detection settings achieve a
strong balance between data cleaning and signal preservation.
In Figure~\ref{fig:threshold_scores}, the threshold value of 3.5 gives the best
overall performance across all four cities, indicating that it is the most suitable
cutoff for separating unusual observations from the normal climatic background.
This is further supported by Figure~\ref{fig:threshold_tradeoff}, where the selected
threshold maintains a favourable balance between removing suspicious values and
retaining a large share of the original data.
The pattern suggests that lower thresholds would risk over-cleaning the dataset,
while higher thresholds would allow more residual anomalies to remain.

The city-wise impact of anomaly refinement can be seen in
Figures~\ref{fig:values_removed} and~\ref{fig:residual_heatmap}.
Mumbai records the highest number of removed values, which is reasonable because
monsoon rainfall and coastal weather variability often produce sharp short-term
changes more likely to be flagged during refinement.
In contrast, Delhi and Jodhpur show fewer removals and very low residual outlier
percentages, indicating a more stable separation between true anomalies and regular
seasonal behaviour.
Dehradun falls in between, with moderate removal counts but still good preservation
of the underlying weather structure.
Taken together, these plots show that the refinement procedure improves overall
data consistency without discarding the meaningful climate patterns needed for
later analysis.

The smoothing refinement results also demonstrate that different cities respond
best to different methods.
Dehradun, Delhi, and Jodhpur achieve their highest composite scores with STL
smoothing using a period of 180, showing that this method is effective at reducing
short-term irregular noise while preserving the broader seasonal signal.
Mumbai performs best with a rolling-window approach of 90, which is likely because
its coastal climate produces smoother long-term variation and less extreme seasonal
contrast than the inland cities.
This difference highlights an important result of the refinement stage: the best
preprocessing choice depends on local climate behaviour rather than a single
universal setting.
By selecting the best method city by city, the smoothed series become easier to
interpret and more suitable for downstream trend and variability analysis.

The extreme-event refinement further improves the reliability of climate-event
identification across regions.
The \texttt{season\_aware\_hybrid} rule set performs best in every city, suggesting
that rules tailored to seasonal context are more effective than rigid global thresholds.
The resulting event counts are also climatologically meaningful: Delhi and Jodhpur
show the highest number of heatwave days, while Mumbai records the strongest
concentration of heavy-rain and extreme-rain events.
Dehradun also shows substantial heavy-rain activity, which fits its topographic
and monsoon-influenced setting.
Because the best-performing rule set aligns closely with expected seasonal timing
and regional weather behaviour, this refinement step increases confidence that the
detected extremes reflect genuine climate events rather than random noise or
artefacts in the raw observations.

\section{Conclusion and Outlook}

Trend analysis confirmed that method choice significantly affects interpretation. 
Specifically, 30-day rolling averages optimise noise reduction, STL decomposition 
reveals coastal vs.\ inland seasonal differences, and harmonic analysis quantifies 
that 65--80\% of the variance is explained by annual cycles.

The data quality assessment showed that GUST and SLP are almost entirely missing 
across all cities, as Indian IMD stations do not transmit these variables to 
NOAA's GSOD database. PRCP retains the highest number of NaN values after cleaning, 
particularly for Mumbai and Dehradun. Record coverage remains close to 365 days 
per year for most cities, with Dehradun in 2000 and Jodhpur in recent years 
being the primary exceptions.

Seasonal analysis indicates that Jodhpur reaches the highest monthly mean 
temperature of approximately 35\textdegree C in May, while Mumbai remains the most 
thermally stable city throughout the year. Mumbai exhibits the sharpest monsoon 
peak, reaching around 390\,mm in July, whereas Jodhpur records the lowest overall 
rainfall. Humidity comparisons further confirm Mumbai's coastal characteristics 
through its consistently narrow temperature--dew point gap, while Jodhpur shows 
the widest gap during winter. 

On interannual scales, Mumbai demonstrates a gradual warming trend from 
approximately 27.5\textdegree C to nearly 29\textdegree C over the period 
2000--2024. Additionally, Dehradun recorded an anomalously high annual rainfall 
of around 2000\,mm in 2013, consistent with the Uttarakhand cloudbursts 
observed in that year.

The refinement stage evaluated three key components: smoothing, anomaly-threshold 
selection, and extreme-event rule tuning using the cleaned weather data for 
Mumbai, Delhi, Dehradun, and Jodhpur. 

For smoothing, rolling windows of 7, 15, 30, 45, 60, and 90 days were compared 
alongside STL periods of 90, 180, and 365 days, as well as harmonic counts of 
2, 4, 6, and 8. The optimal smoothing configuration was achieved using STL 
(period = 180) for Dehradun, Delhi, and Jodhpur, while Mumbai performed best 
with a rolling window of 90 days, indicating that longer seasonal smoothing is 
generally more suitable for most cities.

In anomaly refinement, thresholds ranging from 2.5 to 4.5 were tested. A threshold 
of 3.5 emerged as optimal across all four cities, as it successfully preserved 
known extreme events while minimising residual outliers and additional missing values.

For extreme-event classification, three rule sets---\texttt{imd\_fixed}, 
\texttt{city\_percentile}, and \texttt{season\_aware\_hybrid}---were evaluated. 
Among these, \texttt{season\_aware\_hybrid} consistently achieved the highest 
composite score across all cities.

sensitivity to short-term variability.

for col in ['TEMP_C', 'MAX_C', 'MIN_C', 'PRCP_MM', 'WDSP_MS', 'DEWP_C']:
    monthly_median = df.groupby('MONTH')[col].transform('median')
    monthly_mad    = df.groupby('MONTH')[col].transform(
        lambda x: (x - x.median()).abs().median()
    )
    zscore = np.where(
        monthly_mad > 0,
        0.6745 * (df[col] - monthly_median) / monthly_mad,
        0.0
    )
    is_anomaly = pd.Series(np.abs(zscore) > 3.5, index=df.index)
    df.loc[is_anomaly & ~df['_KNOWN_EXTREME'], col] = np.nan

def rolling_average(data, windows=[7, 30, 90], save_plot=True):
    """Compute and plot rolling averages for given data"""
    results_dir = os.path.join(os.path.dirname(__file__), 'results')
    os.makedirs(results_dir, exist_ok=True)

    fig, axes = plt.subplots(2, 2, figsize=(14, 8))
    axes = axes.flatten()

    for idx, city in enumerate(data['CITY'].unique()):
        city_data = data[data['CITY'] == city].sort_values('DATE').copy()

        for w in windows:
            col = f'rolling_{w}d'
            city_data[col] = city_data['TEMP_C'].rolling(
                window=w, center=True
            ).mean()
            reduction = (
                (city_data['TEMP_C'].std() - city_data[col].std())
                / city_data['TEMP_C'].std() * 100
            )
            print(f"{city} - {w} day window: STD reduced by {reduction:.1f}%")
\end{minted}
